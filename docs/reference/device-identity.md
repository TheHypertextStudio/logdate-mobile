# Device identity

LogDate keeps three different identifiers that are easy to confuse, because each one is a random
UUID and each one is sometimes called "the device's identity". They are created at different times,
survive different events and mean different things. This page defines each of them and then
describes the registry of an account's devices.

| Identifier          | What it names                         | Created                                                                                  | Lost when                                                           |
| ------------------- | ------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| **Device ID**       | One installation of the app           | The first time anything asks for it                                                      | The app is reinstalled, the data is erased, or the person resets it |
| **Canonical owner** | The journal held on this installation | The first time anything asks for it                                                      | The watch is wiped when it is removed from its phone                |
| **Identity key**    | The encryption identity of an account | The first time the app ensures one exists, during onboarding or when sync first needs it | It is replaced by recovering with a different recovery phrase       |

The identity key is described in [Encryption](../explanation/encryption.md). The rest of this page is
about the other two.

## The device ID

The device ID names one installation of the app. It is a random version 4 UUID generated by the
app, so nothing about the machine can be recovered from it and two installations never share one by
accident. The code that
provides it is
[`DeviceIdProvider`](../../client/device/src/commonMain/kotlin/app/logdate/client/device/identity/DeviceIdProvider.kt).
It exposes the current ID as a `StateFlow` so that a reset reaches every collector, and
`refreshDeviceId()` replaces the ID with a new random one.

Every platform generates the ID when it is first read and then reads the stored value on every later
launch. On iOS and desktop, a stored value that is not a valid UUID is replaced by a new one. On
Android, a file that is not exactly 36 bytes stops the read with an "Installation identity needs
recovery" error instead of being replaced, so a damaged file is never silently turned into a new
identity. The platforms differ in where the ID is kept.

| Platform | Where the ID is kept                                                                             |
| -------- | ------------------------------------------------------------------------------------------------ |
| Android  | A file named `.logdate_installation_id` in the app's `noBackupFilesDir`, written atomically      |
| iOS      | The key `device.id` in the device-scoped key-value store, which is backed by the app's DataStore |
| Desktop  | The key `device.id` in the same device-scoped key-value store                                    |

On Android the file is in `noBackupFilesDir` on purpose. The ID names one installation, so it must
not travel in Android's backup to a different installation. A device that is restored from a backup
therefore starts with a new ID. When the file does not exist yet, the ID that the previous key-value
store holds under `device.id` is read once and kept, but only when the installation had already been
initialised and no restore is pending.

Reinstalling the app, or clearing its data, also produces a new ID, because there is nothing left to
read the old one from. The server treats the reinstalled app as a new device.

The ID is not a credential. No authorization decision depends on knowing it, and it carries no
secret. It still identifies an installation, so code logs at most its first eight characters.

### Where the device ID is used

- **Account device registry.** Each device that signs in registers itself under its ID; see the next
  section.
- **Location history.** Every location record names the device that recorded it, so the history of
  several devices merges without collisions.
- **Cloud backup.** A backup attempt records the ID of the device that uploaded it.
- **Data export.** The export metadata and each exported location record carry the ID of the device
  that produced them.

### Resetting the device ID

The Devices screen in settings offers to reset the ID for privacy reasons. A reset generates a new
random ID and registers it with the account. It does not touch the journal, the sign-in or the
encryption keys. The previous ID stays listed under the account.

## The canonical owner

A journal needs an owner from the moment the first entry is written, which can be long before the
person creates an account. The **canonical owner**
([`CanonicalOwnerProvider`](../../client/device/src/commonMain/kotlin/app/logdate/client/device/identity/CanonicalOwnerProvider.kt))
is a random UUID created the first time anything asks for it. It is deliberately independent of the
device ID and of any session: resetting the device ID or signing out never changes it.

The owner starts **unbound**, which means no account has claimed it. When the person creates an
account, the client sends the owner as `requestedOwnerId` and the server uses it as the new account's
ID. That is how the entries written before the account existed already belong to it. After that the
owner is **bound**. Signing in on a second device, where the owner was generated locally and no
account has claimed it, adopts the account's ID as the owner instead. A bound owner refuses to be
rebound to a different account, which keeps one journal from being merged into two accounts.

The owner is kept as two values in the device-scoped key-value store, the owner ID and a flag that
says it is bound. They are read and changed together in one storage transaction, with a conditional
update, so a crash or a second process can never leave an ID that looks bound without a binding. A
bound flag without an owner, or an owner that is not a UUID, is reported as corruption and is never
repaired silently. Removing a linked watch from its phone wipes the watch, including the owner and its
binding, so the next read on the watch creates a fresh, unbound owner.

[Reading identity for native transfer](../../client/device/docs/identity-custody.md) covers how the
owner, the device ID and the keys are read and handed over when a journal moves to another
installation.

## The account's device registry

An account keeps a list of the installations that have signed in to it, so that a person can see them
in settings and recognise one they do not use any more. The server stores the list in the
`account_devices` table and exposes it under `/api/v1/devices`, with a full-access token:

- `GET /devices` returns the account's devices, most recently active first.
- `PUT /devices/{id}` registers a device under its device ID, or updates it.

The `PUT` is an idempotent upsert, so a client can always retry it. It keeps the original
`createdAt` and never moves `lastActive` backwards. It rejects an ID that is not a UUID, a name that
is empty, longer than 120 characters or contains control characters, an app version longer than 64
characters or containing control characters, and a platform other than `ANDROID`, `IOS`, `MACOS`,
`WINDOWS`, `LINUX`, `WEB` or `UNKNOWN`. A watch is not in this list. It does not sign in, and it is
managed as a [linked device session](../../server/docs/device-sessions-api.md).

On the client,
[`CloudDeviceRepository`](../../client/device/src/commonMain/kotlin/app/logdate/client/device/identity/data/CloudDeviceRepository.kt)
keeps the registry usable offline:

- A registration or rename is first written to secure storage as a pending request and then sent. A
  request that fails is retried every time the device list is observed, so a rename made offline
  reaches the server later.
- The device name that the person chose is cached per account and server and is preferred over the
  server's copy, so a rename never flickers back during a refresh.
- While the Devices screen is open, the list is refreshed every five seconds. The last list that
  was received is cached, so the screen can show it with a "could not refresh" state when the server
  is unreachable.
- The cache and the pending request are scoped to the server and the account, so changing either
  one never shows another account's devices.

A device's `DeviceInfo` holds its ID, name, platform, creation and last-active times, the app version
and whether it is the current device. On Android the default name is the name the person gave the
device in system settings, and then the model name. On desktop it is the operating system and host
name. A name that looks like an emulator or build identifier, is empty, or is "unknown" is replaced by
a plain fallback such as "Android device", so the list never shows a build string.

The Android app registers its device when sync is set up and again whenever the Devices screen is
open, and a rename or a reset registers the new details. The shared device manager that does this
is provided on Android and desktop. A device with no signed-in session registers nothing, because
the registry belongs to an account.

## How devices relate to keys and sign-in

Registering a device grants it nothing. What a device can do depends on how it signed in:

- A phone or computer holds full-access tokens from a passkey or Google sign-in. See
  [JWT authentication](../jwt-authentication.md).
- A watch holds a device token from a link code. See
  [linked device sessions](../../server/docs/device-sessions-api.md).
- A new phone or computer can be approved by a device that is already signed in, which also hands it
  the encryption keys. See [Encryption](../explanation/encryption.md#how-keys-reach-another-device)
  and the [device enrollment envelope](./encryption-formats.md#device-enrollment-envelope).
